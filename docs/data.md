### A'. GPS を Parquet に変換した結果（10/1 分で試行、2026-11-15）
- スクリプト: `python scripts/gps_to_parquet.py 2026-10-01`（`all` で31日分）。出力は `data/interim/bus_gps/date=YYYY-MM-DD/part.parquet`。
- **3.42 GB → 0.21 GB（約1/16）、変換 23秒**。31日分でも合計 約6.5 GB・30分程度の見込み。
- 列: `vehicle_id`, `ts`（UTC）, `lat`, `lng`, `speed`, `route_id`, `trip_id`。`date`/`time` は落とした（下記）。
- **3,129万行 → 1,924万行（38% は同じ観測の重複）**。完全に同じ行は無いが、`vehicle_id`＋`timestamp` が同じ行が多い（2回: 423万組、6回以上もある）。`time` 列は GPS の時刻ではなく **取得（ポーリング）した時刻** で、バスが新しい位置を送ってこない間、同じ点が何度も記録されている。`timestamp`（GPS 時刻）で重複を落とすのが正しい。
- `time` と `timestamp` のずれ（＝データの遅れ）は中央値 22秒、90% 点 166秒、99% 点 323秒。リアルタイム推定ではこの遅れを考える必要がある。
- 1台あたりの点の間隔は中央値 11秒。10/1 は車両 6,264台・便 80,636・路線 2,201。
- **31日分の変換結果（2026-11-15）**：合計 **5億6,164万行・5.7 GB**（元の .db は合計 約120 GB）。車両 6,652台・路線 2,305・便 約169万。毎日 3〜4割が重複として落ちた。1日の車両数は 5,632（10/11）〜 6,500 台程度。
- `ts` には前日の深夜の点が少し混ざる（ポーリング時刻では 10/1 でも、GPS の時刻は 9/30 23:30 IST といった古い点）。日ごとの集計は `ts` を IST に直してから日付を切る。
- 緯度経度がデリー周辺から外れた行は 585 行だけ（10/1）。`route_id`・`trip_id` の欠損は無し。
- `speed` は最大 54.7、中央値 8.8、0 が 12%。**単位（km/h か m/s か）は未確認**。位置と時刻から自分で速度を計算して確かめる。

## 3. 容量が大きいデータ（バス GPS）の扱い方

このPCの状況: 空き容量 約119 GB（GPS の .7z を置いた後）、メモリ 32 GB、20 コア。7-Zip・py7zr・polars・pandas は入っている。DuckDB も入れた。

**全部を展開すると 124 GB でディスクがほぼ埋まるので、全展開はしない。** 次の流れで処理する。

1. `.7z`（16.1 GB）だけをダウンロードしてチェックサムを確認する（`curl -C - -O` で途中再開できるようにする）。
2. 7z から **1日分ずつ** `.db`（約4 GB）を取り出す。
3. その日の `.db` を DuckDB などで読み、型を直して（`lat`/`lng` を数値、`timestamp` を整数）、重複を落として **Parquet に変換** する。
4. 変換できたら `.db` は削除して次の日へ。31日分を順に回す。
5. 以降の分析は Parquet を DuckDB / polars で読む（必要な列・期間だけを読めるので 32 GB メモリで足りる）。

- Parquet にすると数分の一〜十分の一程度になる見込み（**未検証の推定**。最初の1日分で実測する）。
- 時間が無ければ、まず平日・休日を含む **1〜2週間分だけ** 変換して手法を作り、残りは検証用に後から足す。
- ローカルで厳しければ、Google Cloud SDK が入っているので GCS＋BigQuery に載せる手もある（費用と利用規約を要確認）。
- チームで共有するときは、生データではなく **変換済みの Parquet** を共有ドライブ等で渡す（利用規約上、チーム外には出さない）。

## 5. 路線数・運行パターン・定員（2026-11-16 集計）

GTFS Static（v32）・バス GPS（10月の31日分、Parquet）・電子乗車券から集計した。

### 路線数

| データ | 路線数 |
|---|---|
| GTFS Static（v32） | **2,574**（DTC 1,814／DIMTS 760）。上り・下りを1本とすると **1,406**（DTC 995／DIMTS 413） |
| GPS（10月中に走った路線） | **2,305**（うち GTFS にあるのは 2,277）。1日あたり 1,853〜2,241（中央値 2,124） |
| 電子乗車券 | 2,259（`8UP`／`8DOWN` のように方向ごと） |

- GTFS の route_id は、ほぼすべてが上り（UP、1,273）か下り（DOWN、1,253）。どちらでもないのは 48。
- 1路線あたりの便数は中央値18、最多303。経路（shape）が1通りの路線は 1,973（77%）。残りの路線には途中止まりなどの別パターンがある。

### 路線は毎日ほぼ同じに運行している
- GTFS の calendar は service_id が1つで、全便が毎日運行（平日・休日の区別なし）。
- GPS では、2,305路線のうち **1,746路線（76%）が31日すべて**、1,904路線が25日以上走っていた。

### 車両は毎日違う路線を走ることが多い（車庫は同じ）
- 1台が1日に走る路線（上り・下りは1本と数える。GPS の点が60点＝約10分以上ある路線だけ）は2〜4本が中心。1路線だけの日は10%。
- 1日のうち最も長く走った路線が前の日と同じなのは **30%**。路線の組み合わせが前の日と完全に同じなのは16%。
- 20日以上動いた車両6,167台では、最も多い路線を走った日は月の **32%（中央値）**。毎日同じ路線を走った車両は **1.2%**。1台が1か月に走る路線は中央値 **19本**。
- 朝の走り始めの地点は、前の日から **1km以内が71%**（3km以内は86%）。→ **車庫は固定で、そこから出る十数本の路線に日替わりで割り当てられている**とみられる。
- 1路線を走る車両は、1日では中央値9台、1か月では75台。**車両番号から路線を決めることはできない**。路線は GPS の route_id／trip_id か、券の `route` で見る。
- 例：DL1PD6928 は 206A → 217・274 → 258・274・254 → 270・335 … と毎日路線が変わっている。

### 定員はオープンデータに無い
- GTFS・GPS・電子乗車券のどれにも定員の列は無い（問題5のブリーフでも「to be confirmed」）。
- 公表値：9m 電気バス DEVI は座席23・定員36、12m 電気バス EiV12 は座席39・定員63、12m CNG車は座席 約40（定員64は試作での仮定）。出典は `reports/所要時間と混雑推定の精度改善策.md`。
- GPS の車両 6,645台の、車両番号の頭の文字による内訳：DL1PD 4,602（非AC の CNG車とみられる）、DL51EV 1,205（電気バス）、DL51GD 685、DL1PE 153。9m車と12m車は車両番号では区別できていない（9m車は全体の26%：経済白書）。

### 注意
- GPS の1日の便数（trip_id の数）は、10/1〜10/10 は 7.3万〜8.7万だが、10/22 以降は 9万〜12万に増えている。trip_id の付け方が変わった可能性があるので、便数で日を比べるときは確認する。
